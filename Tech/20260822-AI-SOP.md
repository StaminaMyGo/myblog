# AI 时代的个人 SOP：从操作手册到动态协议

在 AI 时代，计算机方向的个人 SOP（Standard Operating Procedure，标准作业程序）正经历一场根本性变革：它从一本"死板的操作手册"，进化为一组"可被 AI 编排的动态协议"。

结合 Context 管理、LLM Wiki 和 Agent 编排的相关理念，这套新 SOP 的核心并非约束使用者自身，而是约束 AI 与使用者的协作流程。以下内容介绍构建这套系统的方法论和可落地的操作模板。

## 一、核心理念：从"执行者"到"编排者"

传统 SOP 侧重指导人如何执行（How），而 AI 时代的 SOP 侧重指导 AI 如何协助执行（Orchestration）。

个人 SOP 可拆解为三层架构：

1. **知识底座（LLM Wiki）**：存储"已知正确"的上下文，使 AI 每次开工前自动加载，从而缓解模型遗忘与幻觉问题。
2. **决策路由（Agentic Rules）**：定义不同情境下应采用的流程，防止 AI 在缺乏明确指引时产生不可控的输出。
3. **反馈闭环（Self-Healing）**：每次任务结束后自动复盘并更新 SOP 本身，避免流程僵化。

::: tip 核心理念
AI 时代的 SOP 本质上是一套"给 AI 的约束性宪法"。投入在 SOP 编写上的每一分钟，都在减少未来与 AI 反复沟通、返工的时间消耗。
:::

## 二、实战构建：三步打造 AI-SOP 系统

### 第一步：建立原子化知识库（基建）

避免使用零散的非结构化文件。参考 LLM Wiki 的构建方式，在本地建立 `~/sop_knowledge/` 文件夹：

```text
~/sop_knowledge/
├── context/          # 项目不变的背景信息（架构决策、业务边界）
│   └── my_project_arch.md
├── patterns/         # 可复用的代码范式（错误处理、日志规范）
│   └── python_error_handler.md
├── scripts/          # 固化的自动化脚本
└── SOP_INDEX.md      # 总目录（供 AI 检索）
```

**关键动作**：在项目根目录放置 `AGENTS.md` 文件（或对应工具的规则文件，如 Cursor 的 `.cursorrules`），在文件开头强制写入以下指令：

> 在执行任何代码修改前，必须先读取 `~/sop_knowledge/SOP_INDEX.md` 加载全局约束。

### 第二步：定义状态机式的 SOP 流程（编排）

将日常工作抽象为若干固定的 **State（状态）**，写入 Prompt 或规则文件：

| 状态 (State) | 触发条件 | 执行动作（由 AI 编排） | 退出条件 |
| :--- | :--- | :--- | :--- |
| **需求澄清** | 收到含糊指令 | 强制列出 3 个待确认问题，**禁止**写代码 | 用户确认或补充上下文 |
| **方案设计** | 需求明确，改动较大 | 检索 `context/`，输出影响面分析 + 变更清单 | 用户回复"确认方案" |
| **编码实施** | 方案已确认 | 严格遵循 `patterns/`，单测覆盖率需达标准 | 本地 Lint 及单元测试通过 |
| **复盘归档** | 代码合并后 | 总结踩坑点，决定是否更新 `patterns/` | 生成 changelog |

**提示词模板（放在 `AGENTS.md` 中）**：

> 你是一个严格遵循 SOP 的资深工程师。收到任务后，请按以下流程思考并输出：
> 1. **State 判断**：当前处于哪个状态？
> 2. **Context 加载**：列出本次需要用到的知识库文件路径。
> 3. **Action**：执行当前状态下的具体动作。
> 4. **Checklist**：输出自检清单，确认满足退出条件后才能交给我。

### 第三步：植入自进化钩子（Harness 落地）

在 SOP 中强制增加一个**事后反思（Post-Mortem）** 环节：

> **每次完成任务后，必须执行：**
> 1. 对比"预测耗时"与"实际耗时"，偏差超过 20% 时，标记流程瓶颈。
> 2. 检查本次是否存在"重复性手工操作"。如果有，**必须**编写脚本固化到 `/scripts`，并更新 SOP 中对应的引用。
> 3. 如果本次踩坑（Bug 或环境问题），将解决方案抽象为新的 `pattern`，并提交请求让使用者审核更新知识库。

## 三、计算机方向的具体 SOP 片段示例

针对**后端接口开发**这一高频场景，可按以下方式编写 SOP 片段（可直接喂给 AI）：

**SOP：新 RESTful API 开发规范**

1. **前置确认**：确认数据库表结构变更已通过 Migration 文件管理。
2. **契约先行**：使用 OpenAPI 3.0 编写 YAML 文件，**等待使用者确认**后再写代码，避免无效劳动。
3. **分层编码**：严格遵循 Controller → Service → Repository 三层结构。**禁止**在 Controller 中编写业务逻辑。
4. **错误码映射**：所有业务异常必须映射到 `error_codes.yaml` 中定义的错误码，不允许抛出空指针异常。
5. **测试覆盖**：针对 Service 层编写 Mock 单元测试，针对 E2E 编写集成测试（使用 Testcontainers）。
6. **日志脱敏**：打印任何日志前，自动调用 `mask_sensitive()` 函数，对手机号、身份证号等敏感信息进行脱敏处理。

## 四、如何让这套 SOP 持续运行

- **工具落地**：将 SOP 规则写入 **Cursor Rules**、**GitHub Copilot Custom Instructions** 或 **Claude Projects Instructions**，使 AI 在生成代码前自动过滤 SOP 约束。
- **Context 注入**：在发起大型重构前，手动输入指令："加载 SOP 上下文，我要进行模块拆分"。AI 会自动调取 `context/` 下的架构图，避免偏离方向。
- **版本管理**：将 `~/sop_knowledge/` 目录纳入 Git 管理。当 SOP 更新时，通过 Commit 记录"为何改变做事的逻辑"，这类记录比代码本身的 Git Log 更具长期价值。

## 总结

AI 时代的个人 SOP，本质上是**一套对 AI 协作行为的约束规范**。投入在 SOP 编写上的时间，将在后续的协作过程中通过减少沟通成本、降低返工率获得回报。建议从整理 `README` 和常见 Bug 记录到 `context/` 文件夹开始，逐步构建和完善这套体系。
