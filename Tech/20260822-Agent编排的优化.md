# Agent 编排的优化策略

Agent 编排优化的核心在于将视角从"选择一个好模型"转向"设计一套好系统"。一个低效的编排设计，其 Token 消耗可能是高效设计的数倍。优化的本质，是在**成本、延迟、准确性**三者之间找到最佳平衡点。

## Agent 编排的原理

Agent 编排是指为完成复杂任务，对多个步骤、工具和 Agent 进行组织、协调和调度的过程，相当于系统的"大脑"。

### 核心组件

- **节点（Node）**：工作流的基本单元，如一次 LLM 调用或 API 请求。
- **边（Edge）**：定义节点间的流转逻辑和数据传递方向。
- **有向无环图（DAG）**：用于描述工作流的拓扑结构，确保执行顺序明确且无循环依赖。
- **Context 对象**：在各节点间传递的结构化数据，确保信息在不同阶段保持一致。

### 核心模式

| 模式 | 特点 | 适用场景 | 示例 |
| :--- | :--- | :--- | :--- |
| **ReAct（Reasoning + Acting）** | 动态决策循环，模型边思考边行动 | 代码排错、信息检索等开放任务 | Agent 在调试过程中交替执行"分析错误→搜索文档→修改代码→验证结果" |
| **Plan-and-Execute** | 先规划再执行，分阶段推进 | 目标明确的复杂任务 | 先输出任务分解计划，再按计划逐个执行子任务 |
| **Workflow Graph** | 预定义的确定性流程图 | 规则固化、流程固定的场景 | 数据处理管道，各步骤按固定顺序执行 |

## 优化策略

### 1. 架构精简：做减法

**优先使用单 Agent**：在很多场景下，经过精心设计的单 Agent 能够以更低成本达到接近多 Agent 的效果。例如，将 4 个串行 Agent 合并为 1 个，响应延迟可降低 50% 以上。

**精简 Agent 数量**：Agent 数量与系统能力呈"倒 U 型"关系——过多 Agent 会引入额外的通信开销和协调复杂度。曾有案例将 9 个 Agent 精简到 5 个后，Token 消耗降低 40%。

**职责单一**：确保每个 Agent 或工具具有清晰的职责边界，避免职责重叠导致的隐性内耗和冲突。

### 2. 上下文与状态管理：管好记忆

**减少上下文噪音**：常驻提示词（System Prompt）中只放置核心定义，其他信息通过"三层加载链路"按需注入。动态注入工具描述，避免一次性提供过多工具选择。

**上下文压缩**：使用 Checkpoint 或摘要替代完整历史记录，可使 Token 增长曲线从"平方级"降为"近似线性"。子 Agent 返回摘要而非原始输出，可显著减少后续步骤的上下文体积。

::: tip 上下文压缩实践
当 Agent 执行超过 10 轮交互时，每轮的历史记录将导致 Token 数量快速增长。建议在第 5 轮和第 10 轮分别生成阶段性摘要，丢弃原始对话历史，仅保留摘要。
:::

**状态外置与隔离**：将状态存储在外部系统（如数据库）中，实现断点续跑能力。Agent 之间采用"先隔离，再选择性共享"的策略，避免某一 Agent 的幻觉传播到其他 Agent。

### 3. 执行效率优化：让流程更快

**并行执行**：使用 **Fan-Out/Fan-In** 模式并行处理独立的子任务，可将整体延迟降低 36% 至 50%。例如，在需要同时查询多个数据源时，以并行方式发起请求，汇总结果后再进入下一步。

**异步与缓存**：对 API 调用等耗时操作采用异步非阻塞执行方式，并缓存中间结果，避免重复计算。

**使用确定性路由**：对逻辑明确的分支使用规则判断（如 `if-else` 条件分支），避免将决策权交给不可预测的 LLM，从而减少不必要的 Token 消耗和延迟。

**图剪枝**：移除工作流中的低概率路径，减少不必要的计算分支。在 DAG 中，如果某条路径在历史执行中从未被触发，可以将其剪除，降低系统复杂度。

## 总结

优化 Agent 编排的关键在于**"精设计"而非"选模型"**。具体而言，体现在以下三个转变上：

- **从"给模型更多"到"给模型刚好够用"**：通过上下文压缩和按需加载，避免信息过载。
- **从"堆砌 Agent"到"精简架构"**：追求清晰的职责边界和最小化 Agent 数量。
- **从"串行等待"到"并行加速"**：充分利用并行执行和异步机制，提升系统吞吐量。

Agent 编排本质上是一个**系统工程问题**，其目标是在**成本、延迟、准确性**的三角约束下，找到最适合特定业务场景的最优解。
