# Karpathy 三层 AI 交互法

:::: tip 本文导读
本文整理自视频《别再乱问 Claude，试试 Karpathy 三层法》（原视频：*Stop Prompting Claude. Use Karpathy's Method Instead.*）。核心主张是：**可以外包思考，但不能外包理解**。三层工作流（Spec / Verifier / Environment）用系统化的规格、校验与环境，替代「写一句 prompt 直接收结果」的使用方式，以提升复杂任务的可靠性。
::::

## 一、全文总结

1. **单句 prompt 的问题不在于不够巧妙，而在于缺少约束**：模糊的指令必然带来不稳定的输出，且用户无法判断输出是否正确。
2. **第一层 Spec**：用一份规格文档完整描述任务目标、输入范围、输出规范、已知约束与失败案例，消除歧义。
3. **第二层 Verifier**：建立检查标准，对照 Spec 校验输出是否合格，可人工完成，也可由模型充当评审。
4. **第三层 Environment**：为模型提供项目知识库、工具权限与使用规则，使其无需每次对话重复注入上下文。
5. **定位的转变**：把大模型当作「机器人图书管理员」——擅长检索、整理与生成，而判断标准、目标与责任必须由人掌握。

## 二、背景

### 2.1 常见使用方式的三类缺陷

| 缺陷 | 表现 |
| --- | --- |
| 模型输出自信的错误 | 回答逻辑通顺，但事实、逻辑与细节存在漏洞 |
| 思考过程被整体外包 | 用户不掌握判断标准，无法识别输出对错 |
| 难以处理复杂任务 | 在编码、方案设计、系统构建类任务上，产出质量极不稳定 |

### 2.2 问题根源

缺陷的共同根源不是提示词写得不好，而是**缺少三层结构**：没有明确的规格，模型只能按最通用的方式猜测；没有校验环节，错误不会被发现；没有稳定环境，每次对话都要从零补充上下文。

## 三、三层交互工作流

### 3.1 第一层：Spec（详细规格说明书）

核心是**把任务完整、精确地写清楚，消除所有模糊性**。不是简短提问，而是产出一份规格文档（例如 `Claude.md`），明确全部约束条件：

| 要素 | 内容 |
| --- | --- |
| **业务目标** | 这件事最终要达成什么效果 |
| **输入范围** | 允许模型使用哪些资料、文件与上下文 |
| **输出规范** | 输出格式、结构、禁止行为、风格、边界条件 |
| **已知约束** | 限制、禁忌、不能修改的部分 |
| **失败案例** | 举例说明哪些输出是错误、不可接受的 |

**目的**：杜绝歧义。Spec 相当于给模型一份完整的任务手册，而不是一句口头命令。

:::: note 失败案例的价值
多数规格文档只包含「要什么」，缺少「不要什么」。补充失败案例可以显著降低模型在边界情况下的错误率，因为它把抽象标准转化为具体对照样本。
::::

### 3.2 第二层：Verifier（验证器）

核心是**建立一套标准，用来检查生成结果是否合格**。验证分两种形式：

1. **人工验证**：对照 Spec 逐条复核产出，检查是否满足全部要求；
2. **AI 辅助验证**：把 Spec 与模型输出一并交回大模型，让其充当评审，输出校验报告并标记不符合项、漏洞与错误点。

**关键点**：验证器的判断标准来自第一层的 Spec，而不是人的临时感觉。若验证不通过，将发现的问题反馈给模型迭代修改，循环直到满足规格。

**两层关系的概括**：第一层规定「要做成什么样」，第二层检查「有没有做成那样」。

### 3.3 第三层：Environment（环境）

核心是**为模型搭建可用的上下文、工具与知识库环境**，使其具备完成任务所需的现实条件。

| 组成部分 | 内容 |
| --- | --- |
| **项目知识库** | 相关文档、代码库、参考资料、规则文件（如 `Claude.md`） |
| **工具权限** | 文件读写、检索、代码运行等能力 |
| **规则约束** | 工具使用规则、访问边界、上下文加载规则 |

Environment 解决的是一个具体问题：**模型不能凭空掌握项目背景**。应把必要信息放进它的工作环境，而不是在每次对话中重复粘贴。

## 四、完整运行闭环

```text
准备 Environment（知识库 + 规则文件）
        ↓
编写 Spec（明确目标、约束、输出标准）
        ↓
模型读取环境 + Spec，生成初步结果
        ↓
Verifier 对照 Spec 校验输出
        ↓
├─ 校验通过 → 交付最终结果
└─ 校验不通过 → 将问题反馈给模型，回到生成环节迭代
```

## 五、核心思想与实践启示

1. **可以外包思考，但不能外包理解**：模型可以整理、推演与生成内容，但对业务的理解、对错的判断标准必须属于人。自己不理解的领域，不应完全交给模型决定。
2. **Prompt 只是表层，系统工作流才是关键**：复杂任务的质量瓶颈不在一句话 prompt，而在清晰的规格、严格的校验与完备的上下文环境。
3. **模型定位为「机器人图书管理员」**：不要期待模型理解业务；应由人写清规则、提供资料，让模型在划定的框架内工作。
4. **适用与不适用场景**：

| 场景 | 收益 |
| --- | --- |
| 代码开发 | 高 |
| 方案撰写 | 高 |
| 项目分析 | 高 |
| Agent 构建 | 高 |
| 复杂文档生成 | 高 |
| 简单日常问答 | 低 |

:::: warning 成本提示
三层法的收益来自前期的规格与知识库投入。对于一次性、低价值的简单任务，构建 Spec 与环境的成本可能超过收益；它更适合需要反复执行、对正确性有要求的任务。
::::

## 六、落足当今的现实意义

1. **输出质量的上限由规格决定，而非由模型决定**：当模型能力趋于同质时，差异主要来自任务描述的精度。把需求文档化，是成本最低、收益最稳定的改进项。
2. **校验环节是把「可用」变为「可信」的关键**：模型错误的主要风险在于难以察觉。建立可对照的校验标准，使错误在交付前被发现，是引入 AI 到正式工作流的前提。
3. **上下文一次构建、多次复用**：Environment 层把重复粘贴信息的成本转化为一次性投入，对长期项目尤其明显。
4. **责任边界需要明确**：可以外包思考过程，但不能外包理解与判断。这一原则同样适用于代码审查、文档生成与数据分析等场景——最终判断必须由能够承担后果的人做出。

:::: tip 一句话总结
第一层规定「要做成什么样」，第二层检查「有没有做成那样」，第三层提供「完成任务所需的条件」；三者构成闭环，把单句提示词升级为可复用的工作流。
::::

## 七、名词释义

| 名词 | 释义 |
| --- | --- |
| Spec（规格说明书） | 完整描述任务目标、约束条件、输出格式与禁忌要求的文档，用于消除任务歧义并作为全部工作的基准，典型如 `Claude.md` |
| Verifier（验证器） | 校验环节：对照 Spec 检查输出是否合格，可人工完成，也可由大模型充当评审识别错误与不满足项 |
| Environment（环境） | 模型的工作底座，包含项目知识库、参考资料、工具权限与访问规则，提供完成任务所需的上下文 |
| LLM（大语言模型） | 能够理解文本并生成内容的模型，容易产生看起来合理但实际错误的输出 |
| Prompt | 用户发给模型的提示或指令；普通用法依赖单句 prompt，三层法则将其升级为完整的文档化工作流 |
| Claude.md | Karpathy 工作流中常用的项目规格文件，集中存放项目 Spec、规则与知识库指引 |
| Agent（智能体） | 能够自主调用工具、迭代完成复杂多步骤任务的 AI 程序；三层法是构建可靠 Agent 的底层思路之一 |
