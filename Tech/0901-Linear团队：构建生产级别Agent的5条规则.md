# 构建生产级别 Agent 的 5 条规则

:::: tip 本文导读
本文整理自 B 站视频《Linear 团队：构建生产级别 Agent 的 5 条规则》（分享者：Nan Yu、Jacob Shumway，Linear 团队；转述整理：Easonlee）。内容复盘了 Linear 从 Slack 机器人演进到可提交 PR 的工程化智能体系统的过程，重点在产品化与工程化落地思路，而非提示词技巧。
::::

## 一、全文总结

1. **Agent 的核心价值是循环迭代，而非单次问答**：它是目标驱动循环系统，除模型外还需要调度层、交互层、权限控制与状态管理。
2. **先接管枯燥重复工作，再拓展到创造性工作**：落地起点应是人类不愿做的机械性事务，而非追求全能。
3. **把 Agent 部署在用户本来就在工作的地方**：不人为创造新入口，工作发生的场景即触发入口。
4. **拒绝全量 API 灌入，采用技能按需加载**：控制上下文长度，抑制幻觉，同时保留完整业务能力。
5. **产出必须是可追踪的实体结果**：把口头共识固化为系统内的任务、负责人与代码，而不是生成漂亮的 Markdown 文本。

## 二、背景

### 2.1 Linear 的演进路径

| 阶段 | 形态 | 能力 |
| --- | --- | --- |
| 起点 | 机器人项目经理 | 自动化工单记录、进度跟进等重复事务 |
| 中间态 | Slack 工作流中的隐秘上线 Agent | 在真实用户环境中测试与迭代 |
| 目标态 | 嵌入研发工作流的工程化智能体 | 读取讨论、梳理共识、创建任务、分配负责人、6 分钟生成并提交 PR |

### 2.2 核心认知

> 生产级 Agent ≠ 聊天框调用大模型，而是一套包含目标循环、工具调度、权限体系、交互入口与技能管理的完整系统。

## 三、五条规则

### 规则一：Agent 的核心价值是循环迭代，而非单次问答

Agent 本质是**目标驱动循环系统**：

```text
接收目标 → 调用工具获取信息 → 判断现状 → 补齐缺失信息 → 反复执行动作 → 校验目标是否完成
```

- **常见误区**：把 Agent 等同于聊天对话，只关注模型输出的文本；
- **完整构成**：除大模型外，还需要调度层、交互层、权限控制与状态管理等子系统；
- **价值来源**：单次模型回答能力有限，价值来自多轮工具调用与信息补齐的闭环。

### 规则二：优先把枯燥重复工作交给 Agent

- **项目起点**：自动化记录工单、跟进进度、同步消息等人类不愿做的琐事；
- **实践结果**：随着能力迭代，Agent 不再局限于琐事，可深度参与讨论、决策与代码实现等创造性工作链路；
- **落地启示**：不要一开始就追求全能，先解决人类厌恶的机械工作，再逐步拓展能力边界。

### 规则三：隐秘上线，把工作场所作为自然语言入口

Linear 没有做表单式固定交互界面，而是直接在 Slack 环境中接入 Agent，用户通过 @ 触发。

- **用户行为特征**：不需要复杂指令，简单表达「做该做的事」甚至发送表情符号，Agent 读取聊天上下文后自动推断待办事项；
- **关键启发**：**不要人为创造新入口，Agent 应部署在用户本来就在工作的地方**；聊天框更多用于后续追问，而不是主要触发入口。

### 规则四：拒绝全量 API 灌入，采用技能按需加载

:::: warning 踩坑经历
最初把全部操作接口与 GraphQL Schema 全部交给大模型，导致上下文窗口爆炸、幻觉严重，性能与效果同时恶化。
::::

**解决方案：技能（Skill）按需加载机制**

1. 将能力拆分为独立技能包，每个技能只携带少量配套工具与业务操作规范；
2. Agent 根据当前任务只加载需要的技能，而非全部能力；
3. 将产品业务标准、工单质量规范编码写入技能内部。

**收益**：控制上下文长度、抑制幻觉，同时保留完整业务能力。

### 规则五：核心产出是把讨论转化为可追踪的实体结果

**经典案例**：Slack 中的设计讨论，当团队说出「直接做吧」，Agent 自动完成整套链路：

```text
读取聊天记录 → 梳理共识结论 → 创建项目 Issue → 指定负责人 → 生成代码 → 提交 PR（约 6 分钟）
```

- **痛点**：团队大量决策消散在聊天记录中，没有沉淀为任务、代码与待办；
- **价值定位**：Agent 的价值不是生成漂亮的 Markdown 文本，而是把口头共识固化为系统内可追踪、可执行的工作产物。

## 四、评测体系设计

| 输出类型 | 评测方式 |
| --- | --- |
| **确定性任务** | 校验系统状态是否被正确修改（任务是否创建、负责人是否指定） |
| **非确定性输出**（标题、描述文案质量） | 使用模型做评判，并持续收集真实失败案例迭代数据集 |

**设计原则**：

- 不追求输出结果千篇一律，容忍合理的输出多样性；
- 评测重点防范两类风险：**误判用户意图**、**未经许可擅自执行动作**；
- 不需要对 Agent 的每一步行为做强硬约束。

## 五、原生 Agent 的护城河

| 做法 | 结果 |
| --- | --- |
| **反例**：只对外提供 MCP 协议与一堆工具集合，交由用户自行拼装 | 产出大量没人阅读的冗长 Markdown 文档 |
| **正解**：把产品对业务流程的理解内置到技能与默认流程中 | 深度承接完整的软件开发生命周期 |

**结论**：护城河不在工具本身，而在于内置的行业工作方法论与默认行为范式。

## 六、工作流拆解与演进方向

1. **触发源优先级**：Slack 讨论、会议纪要、项目更新等真实工作发生场景；
2. **聊天界面的定位**：用于后续追问与补充信息，而不是主要工作触发入口；
3. **演进方向**：增加持久记忆与主动能力，在项目完整周期内自动推进协调与文档更新。

## 七、落地避坑对照表

| 常见错误做法 | Linear 推荐的生产级方案 |
| --- | --- |
| 将 Agent 等同于聊天界面，只优化提示词 | 将 Agent 当作完整系统，重视循环、调度、权限与技能架构 |
| 一次性把全部 API、Schema 灌入上下文 | 技能按需加载，控制上下文，业务规则编码进技能 |
| 新建独立 Agent 页面，要求用户切换场景 | 嵌入现有工作环境，工作发生处即为触发入口 |
| 评测强制 Agent 输出固定文本格式 | 评测聚焦用户意图，管控风险，容忍合理输出多样性 |
| 只提供工具让用户自行组合 | 内置业务流程范式，产出可追踪的真实业务对象（任务、PR） |

## 八、落足当今的现实意义

1. **上下文是稀缺资源，应按任务动态分配**：把全部能力一次性暴露给模型，会同时损害效果与成本。技能按需加载是把上下文当作预算来管理的工程实践。
2. **入口选择决定使用频率**：要求用户切换场景是采纳率下降的主要原因之一。Agent 的触发点应位于工作已经发生的地方，而不是新建的独立页面。
3. **可追踪的产出才是业务价值**：生成文本不等于完成工作。判断 Agent 是否真正产生价值，看它是否在系统内创建了可被跟踪与流转的对象。
4. **评测应关注意图与风险，而非格式一致性**：强制固定输出会牺牲模型的适应性与输出质量；重点应放在是否理解用户意图，以及是否在授权范围内行动。
5. **工具不是壁垒，内置的工作范式才是**：当工具与协议趋于标准化后，差异化来自对业务流程的理解——即默认如何拆解任务、如何推进流转、如何交付结果。

:::: tip 一句话总结
生产级 Agent 是一套系统而非一个对话框：用循环替代单次问答，用技能按需加载控制上下文，用现有工作场景作为入口，用可追踪的实体结果作为交付物，用意图与风险作为评测重心。
::::

## 九、名词释义

| 名词 | 释义 |
| --- | --- |
| Agent（智能体） | 以目标为导向，可自主调用工具、获取信息、循环执行动作并完成复杂任务的 AI 系统，不止是对话大模型 |
| 生产级别 Agent | 可正式上线给真实用户使用，稳定、可控、可维护，能融入业务工作流的智能体系统，区别于 Demo 原型 |
| PR（Pull Request） | 代码合并请求，开发者提交代码后用于评审并合并进项目主代码库 |
| GraphQL Schema | GraphQL 接口的描述定义，定义系统可访问的数据与提供的操作接口 |
| 幻觉（Hallucination） | 模型生成不存在或不符合事实的错误信息 |
| 技能（Skill） | Agent 的能力封装单元，绑定一组工具与业务规则，按需加载以避免上下文膨胀 |
| MCP | Model Context Protocol，模型上下文协议，用于标准化地向 AI Agent 暴露工具能力 |
| 上下文窗口 | 大模型单次可读取处理的全部文本长度上限，数据过多会触发上下文溢出 |
| Issue | 项目管理工具中的任务／缺陷条目，记录需求、Bug 与待开发工作 |
