# Electron 打包：从应用分发到工程化交付

Electron 打包的核心作用，是把使用 Web 技术（HTML、CSS、JavaScript）开发的应用，转换成可以在 Windows、macOS 和 Linux 上直接运行的**原生桌面安装包**，例如 Windows 下的 `.exe`、macOS 下的 `.dmg` 等。

其运用场景主要集中在两个方面：**应用分发**与**开发交付**。下文分别展开说明。

## 一、核心运用：将应用交付给终端用户

将应用交付给终端用户是 Electron 打包最主要的目的。完成应用开发后，需要通过打包产出可供用户下载、安装的最终文件。

### 1.1 为不同平台生成安装包

Electron 支持跨平台打包，可以在一个系统上同时为 Windows、macOS 和 Linux 生成对应的安装包：

- **Windows**：生成 `.exe` 安装程序或 `.msi` 安装包；
- **macOS**：生成 `.app` 应用包或 `.dmg` 磁盘映像文件；
- **Linux**：生成 `.deb`（Debian/Ubuntu）或 `.rpm`（Red Hat/Fedora）等安装包。

### 1.2 配置应用身份信息

打包时可以为应用设置**自定义图标**、**修改应用名称**、**版本号**等元信息，使其呈现为独立的、品牌化的桌面软件。

### 1.3 实现应用的自动更新

自动更新通常依赖后续的"发布"流程，但打包是基础。将安装包通过 `electron-forge publish` 等命令上传到服务器或 GitHub Releases 后，可以配合更新机制，让用户收到新版本的推送通知。

## 二、开发与工程化运用：优化开发和交付流程

打包不仅用于最终分发，也在开发过程中扮演重要角色。

### 2.1 开发阶段的调试与预览

在开发环境中，可以通过运行 `npm run electron:serve` 或类似命令，在桌面环境中实时预览和调试应用。正式打包前，也可以先执行 `electron-forge package` 命令，生成一个未压缩的可执行文件夹，用于测试打包后的应用是否正常运行。

### 2.2 集成 CI/CD 流水线

对于团队协作或正式项目，打包过程可以集成到持续集成/持续部署（CI/CD）流水线中（例如 GitHub Actions）。每次代码更新后，系统可以自动完成应用的打包、代码签名和发布，实现自动化交付。

### 2.3 处理原生依赖

如果应用使用了需要编译的 Node.js 原生模块，打包工具（如 `@electron/packager`）会在打包过程中为当前 Electron 版本**重新构建（Rebuild）这些模块**，确保它们在桌面环境中能正常运行。

:::: tip 说明
原生模块（如 `node-sass`、`sqlite3` 等）通常针对本机 Node.js 版本编译，与 Electron 内置的 Node 运行时版本并不一致。打包工具会自动触发 rebuild，是打包流程中容易遗漏但必须处理的环节。
::::

## 三、主要打包工具

实际开发中会接触到两个主要工具，它们的关系如下：

| 工具 | 定位 | 说明 |
|------|------|------|
| [Electron Forge](https://www.electronforge.io/) | 一站式、全流程工具 | 集成了创建项目、代码签名、生成安装包、发布更新等功能，是官方推荐的解决方案 |
| [@electron/packager](https://www.npmjs.com/package/@electron/packager) | 核心基础工具 | 主要负责将应用源码与 Electron 运行时合并成可执行文件夹 |

**关系说明**：Electron Forge 内部正是使用 `@electron/packager` 完成其第一步（Package）工作。也就是说，`@electron/packager` 是更底层的能力，而 Forge 在此基础上提供了更完整的工程化流程。

:::: warning 注意
通常情况下直接使用 **Electron Forge** 会更省心，因为它将多个工具的配置和流程整合在一起。仅在需要高度定制打包流程、且不需要发布与更新功能时，才考虑单独使用 `@electron/packager`。
::::

## 四、打包流程的一般步骤

无论是使用哪套工具，Electron 打包通常遵循以下步骤：

1. **编写应用代码**并确保开发环境运行正常；
2. **配置打包选项**：应用名称、图标、版本号、平台目标、原生模块 rebuild 策略等；
3. **执行 Package**：生成未压缩的可执行文件夹，验证产物可用；
4. **生成安装包**：将可执行文件夹封装为目标平台的安装程序（`.exe`、`.dmg`、`.deb` 等）；
5. **签名与公证**（发布前）：macOS 需要签名与公证，Windows 需要代码签名证书，否则可能触发系统安全警告；
6. **发布**：将安装包上传至分发渠道，配合自动更新机制向用户推送。

## 五、常见问题与排查思路

| 问题 | 可能原因 | 排查方向 |
|------|---------|---------|
| 打包后应用无法启动 | 原生依赖未 rebuild 或版本不匹配 | 检查打包日志中的 rebuild 步骤，确认 Electron 版本与模块版本 |
| 安装包体积过大 | 未排除无用资源、`node_modules` 未裁剪 | 使用 `files` 配置精简打包内容，排除开发依赖 |
| 触发系统安全警告 | 缺少代码签名 | Windows 使用代码签名证书，macOS 执行签名与公证流程 |
| 跨平台打包产物异常 | 平台特有 API 或路径分隔符问题 | 在目标平台进行真机验证，或使用 CI 多平台流水线 |

## 六、总结

- Electron 打包将 Web 技术开发的应用转化为可分发、可安装的桌面应用；
- 其价值覆盖**最终分发**与**开发工程化**两个层面，且可接入 CI/CD 实现自动化交付；
- Electron Forge 与 `@electron/packager` 是配套关系，前者为推荐的首选方案；
- 打包涉及原生依赖 rebuild、代码签名、安装包生成等关键环节，需要按步骤验证产物可用性。
