## 一、任务概览：输入、约束与交付物

### 1.1 任务定义

| 维度 | 具体要求 |
|:---|:---|
| **核心目标** | 详细总结B站408学习方法视频的内容 |

### 1.2 任务的隐性挑战

任务表面上有两项显性需求：总结视频内容、生成 Markdown 文件。实际执行中还存在多个隐性挑战：

- **内容来源**：视频无法直接观看，需要找到文字稿或配套文档；
- **读取方式**：飞书 Wiki 需要专用工具读取，不能用普通 web fetch；
- **跨环境访问**：参考文件在 Windows F 盘，Linux 环境无法直接访问；
- **可视化要求**：需要 Mermaid 图表，而非纯文字罗列；
- **术语处理**：专业术语需要系统整理，而非零散解释。

> **探查阶段的核心原则**：不要急于开始写作，先确认**内容来源的可靠性和完整性**。一个错误的内容来源会导致整个后续工作建立在沙子上。

## 三、阶段一：输入探查——从视频页面提取关键线索

### 3.1 输入源分析

任务的原始输入是一个B站视频页面。由于**无法直接播放视频提取音频/字幕**，必须从页面元信息中找到文字内容的替代来源：

1. 视频页面包含标题（"为什么你学408像在学天书？"）、UP主（潜水的根号二）、视频简介区、评论区置顶四类信息来源；
2. 视频简介区出现关键线索：文档链接 `riil8bn9ykt.feishu.cn/wiki/...`；
3. 评论区重复出现同一链接，确认这是视频配套文档；
4. 飞书 Wiki 即视频内容的文字稿/讲义。

### 3.2 关键决策：为什么选择飞书文档而非其他途径

| 备选途径 | 可行性 | 选择/放弃理由 |
|:---|:---:|:---|
| **飞书Wiki配套文档** | ✅ 高 | 视频简介和置顶评论都指向同一链接，UP主明确说"大家一定要看视频！视频讲的更详细！"并附文档——这是官方配套文字稿 |
| **视频字幕提取** | ❌ 低 | 页面显示"暂无字幕"，且无法直接播放视频提取音频转文字 |
| **第三方视频内容搜索** | ❌ 低 | 无法保证内容完整性和准确性，且可能涉及版权问题 |
| **根据标题和评论推测内容** | ❌ 低 | 评论区只有15条，信息不足以支撑"详细总结" |

## 四、阶段二：技能发现——Skill路由与文档加载

### 4.1 技能路由决策树

飞书Wiki链接需要专用工具读取。系统中存在多个可能相关的Skill，路由规则如下：

- **URL 路径模式判断**：
  - `/wiki/` 路径：进一步判断操作类型——读取文档内容走 `lark-doc` skill（支持 `/wiki/` 读取）；管理知识库结构/成员走 `lark-wiki` skill；
  - `/docx/` 路径：走 `lark-doc` skill；
  - `/sheet/` 路径：走 `sheet` skill。
- **读取链路**（逐级读取文档）：
  1. `lark-doc/SKILL.md`（顶层路由文档）；
  2. `lark-doc/online-doc/lark-doc-skill.md`（在线文档模块）；
  3. `lark-doc/online-doc/references/lark-doc-fetch.md`（`+fetch` 命令参考）；
  4. 并行读取 `lark-wiki/SKILL.md`，确认 `lark-doc` 的 `+fetch` 支持 `/wiki/` URL，无需额外解析 node_token；
  5. 执行 `lark-cli docs +fetch`。

### 4.2 为什么需要逐级读取4个文档

| 读取顺序 | 文件 | 作用 | 关键信息获取 |
|:---:|:---|:---|:---|
| 1 | `lark-doc/SKILL.md` | 顶层路由，判断操作对象和交付载体 | 确认飞书Wiki属于"在线文档"，路由到online-doc模块 |
| 2 | `lark-doc/online-doc/lark-doc-skill.md` | 在线文档模块的场景路由 | 确认"读取/摘要"场景使用`+fetch`，需要先读参考文档 |
| 3 | `lark-doc/online-doc/references/lark-doc-fetch.md` | `+fetch`命令的详细参数说明 | 获取`--doc`、`--doc-format markdown`、`--as user`等参数用法 |
| 4 | `lark-wiki/SKILL.md`（并行读取） | 确认Wiki节点的处理方式 | 确认lark-doc的`+fetch`支持`/wiki/` URL，无需额外解析node_token |

> **Skill加载的强制规则**：不能仅凭Skill描述就直接调用工具，必须先Read对应SKILL.md和参考文档，确认参数结构和调用方式。这避免了参数猜错导致的调用失败。

### 4.3 技能发现阶段的工具调用统计

阶段二仅使用了 Read 工具 4 次（Bash、Write、其他均为 0 次），全部用于读取 Skill 文档与参考文档。

## 五、阶段三：内容获取——lark-cli抓取飞书Wiki全文

### 5.1 命令构造与执行

使用的命令形式为：

```bash
lark-cli docs +fetch --doc '<飞书Wiki URL>' --doc-format markdown --as user
```

CLI 内部处理流程依次为：

1. 解析 `/wiki/` URL，提取 node_token；
2. 调用 wiki API，获取 obj_token 和 obj_type；
3. 调用 docx API，获取文档 blocks；
4. 转换为 markdown 格式；
5. 返回完整文档内容（JSON 包裹）。

### 5.2 关键参数选择理由

| 参数 | 取值 | 选择理由 |
|:---|:---|:---|
| `--doc` | 完整飞书Wiki URL | `+fetch`支持直接传入`/wiki/` URL，CLI会自动解析node_token和底层doc_token |
| `--doc-format` | `markdown` | 任务最终输出是Markdown，直接获取markdown格式减少格式转换损耗；XML格式需要额外解析 |
| `--as` | `user` | 文档是用户个人资源，以user身份调用确保有权限读取；显式指定避免身份歧义 |
| `--scope` | （省略，读取整篇） | 需要完整内容做详细总结，不做局部读取 |
| `--detail` | （省略，默认simple） | 只读场景不需要block ID和样式元数据，simple模式输出更简洁 |

### 5.3 获取结果分析

返回结构包含以下关键信息：

- `ok: true`：请求成功；
- `identity: user`：以用户身份访问；
- `document_id`：文档标识；
- `revision_id: 847`：文档修订号；
- `content`：完整 markdown 内容，包含标题、6大章节+结尾总结、约5000字正文，并引用翁恺老师的经典论述。

> **revision_id: 847** 说明这份文档经过了847次修订，是UP主反复打磨的高质量内容，值得详细总结。

## 六、阶段四：内容结构化——从原文到七板块知识框架

### 6.1 原文结构 vs 输出结构的映射

获取到的原文有6个章节，但直接按原文结构输出会导致"内容碎片化"（用户明确要求不碎片化）。重新组织后的映射关系如下：

| 原文结构（6章） | 输出结构（7板块 + 附录） |
|:---|:---|
| 1. 学习的方法和观念 | 一、核心观念重构（计算机科学的本质） |
| 2. 我们需要怎样学习408 | 二、系统化学习（从碎片到体系） |
| 3. 学会计算机科学的语言 | 三、术语体系（进入计算机科学的语言） |
| 4. 学习中的输入与输出 | 四、输入与输出（学习的闭环） |
| 5. 学习和应试之间 | 五、学习与应试（深度的取舍） |
| 6. 怎样看待考频分析 | 六、考频分析（工具而非主宰） |
| 全部章节 | 七、总结框架（思维导图+行动清单） |
| 全部章节 | 附录：专业术语释义表 |

### 6.2 结构化的三个原则

| 原则 | 具体做法 | 在本任务中的体现 |
|:---|:---|:---|
| **① 不照搬原文目录** | 重新提炼板块标题，使其反映"认知层次"而非"原文顺序" | 原文"学习的方法和观念"→输出"核心观念重构：计算机科学不是自然科学" |
| **② 增加统合层** | 在各板块之上增加总结框架层，用思维导图统合全部内容 | 第七板块"总结框架"用mindmap将五维（观念/体系/语言/方法/应试）统合 |
| **③ 术语独立成表** | 专业术语不分散在正文中解释，而是集中到末尾表格 | 附录收录28个术语，每个含定义/起源/区分点 |

### 8.3 交付机制：present_files

交付链路依次为：

1. 本地文件路径（`.../0907-xxx.md`）作为输入；
2. 调用 present_files 工具；
3. 文件上传到 CDN；
4. 生成可访问 URL（`aka.doubaocdn.com/s/...`）；
5. 客户端渲染文件预览；
6. 用户可下载/查看。

> **为什么用present_files而不是直接给路径**：用户在Windows环境，文件生成在Linux容器中，直接给路径用户无法访问。present_files会上传文件到CDN并生成可下载链接，实现跨环境交付。

## 九、工具链全景：四类工具的协同

### 9.1 工具调用总览

按职能划分为五组：

- **信息获取类**：Read 工具（读取 Skill 文档和参考文件）、Bash + lark-cli（抓取飞书 Wiki 内容）；
- **创作输出类**：Write 工具（一次性写入 Markdown 文件）；
- **验证类**：Bash + wc/grep（统计行数/图表数/表格数）；
- **交付类**：present_files（上传 CDN 生成下载链接）；
- **任务管理类**：TodoWrite（跟踪任务进度，全程参与）。

调用依赖顺序为：信息获取类 → 创作输出类 → 验证类 → 交付类；TodoWrite 在全程跟踪各阶段。

### 9.2 各工具调用次数与作用

| 工具 | 调用次数 | 阶段 | 具体作用 |
|:---|:---:|:---:|:---|
| **Read** | 4次 | 阶段二 | 读取lark-doc SKILL.md、lark-wiki SKILL.md、lark-doc-skill.md、lark-doc-fetch.md |
| **Bash** | 2次 | 阶段三、六 | ① lark-cli docs +fetch 抓取文档；② wc/grep 验证文件统计 |

| **TodoWrite** | 4次 | 全程 | 任务进度跟踪（创建→更新→完成） |

### 9.3 工具链的依赖关系

工具链的核心依赖链为：

1. Read（技能文档）→ 提供命令参数 → Bash: lark-cli（内容获取）；
2. Bash: lark-cli → 提供原文内容 → Write（文件生成）；
3. Write → 生成本地文件 → Bash: wc/grep（验证统计）；
4. Bash: wc/grep → 验证通过 → present_files（交付）；
5. TodoWrite（进度跟踪）贯穿上述各环节。

## 十、关键决策与取舍

### 10.1 决策点汇总

| 决策 | 内容 | 理由 |
|:---:|:---|:---|

### 10.2 取舍的代价与收益

## 十一、可复用工作流模板

### 11.1 通用模板：视频/音频内容的文字总结

执行步骤依次为：

1. **探查**：寻找文字稿/配套文档/字幕；
2. **路由**：根据文档类型选择 Skill——飞书 → lark-doc；网页 → web.fetch；PDF → doubao-pdf；
3. **获取**：用对应工具抓取完整内容；
4. **结构化**：提炼框架，设计可视化方案；
5. **创作**：写入 Markdown（Mermaid + 表格 + 术语表）；
6. **验证**：行数/图表数/术语数量化校验；
7. **交付**：present_files 生成下载链接。

若未找到文字来源，则走备选路径：视频提取工具/语音转写，或如实告知用户内容获取受限。

### 11.2 各阶段的检查清单

| 阶段 | 检查项 | 通过标准 |
|:---:|:---|:---|
| **① 探查** | 是否找到可靠的文字内容来源？ | 来源是官方/作者提供，或经过交叉验证 |
| **② 路由** | 是否读取了对应Skill的SKILL.md和参考文档？ | 至少读取顶层SKILL.md + 具体命令参考文档 |
| **③ 获取** | 是否获取了完整内容（非截断）？ | 内容包含开头到结尾，无"..."省略 |
| **④ 结构化** | 是否设计了不碎片化的框架？ | 有统合层（总结/思维导图），板块间有逻辑递进 |
| **⑤ 创作** | 是否满足所有格式要求？ | 命名规范、可视化丰富、术语表在末尾 |
| **⑥ 验证** | 是否通过量化校验？ | 行数/图表数/术语数达到预期阈值 |
| **⑦ 交付** | 用户是否能获取文件？ | present_files返回可访问URL |

### 11.3 本工作流的适用边界

| 适用场景 | 不适用场景 |
|:---|:---|
| 有配套文字稿/文档的视频总结 | 完全没有文字来源且无法转写的视频 |
| 飞书/Notion/语雀等在线文档的内容总结 | 需要实时播放/交互的视频分析 |
| 需要结构化输出（Markdown+图表+术语表）的学习笔记 | 简单的一句话摘要或标题提取 |
| 专业知识类内容（需要术语整理） | 娱乐类/纯视觉类内容 |

## 十二、效率分析与优化方向

### 12.1 时间分布

各阶段时间占比（估算）：阶段一输入探查约 10%、阶段二技能发现约 20%、阶段三内容获取约 10%、阶段四内容结构化约 25%、阶段五创作输出约 25%、阶段六验证交付约 10%。内容结构化与创作输出合计占一半以上，是耗时的主要部分。

### 12.2 瓶颈与优化

| 阶段 | 当前瓶颈 | 优化方向 | 预期收益 |
|:---|:---|:---|:---|
| **技能发现** | 需要逐级读取4个文档，耗时较长 | 建立常用Skill的参数速查表，减少重复读取 | 节省50%技能发现时间 |
| **内容结构化** | 需要人工推理框架和可视化方案 | 建立内容类型→框架模板的映射库 | 减少结构化推理时间 |
| **创作输出** | Write是一次性写入，出错需要整体重写 | 支持分块写入+增量编辑（需工具升级） | 降低重写成本 |
